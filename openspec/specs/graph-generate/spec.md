# graph-generate Specification

## Purpose

Graph production — the maker journey. An end user (no repo-owner assumptions) produces a NEW workflow graph (`.yaml`) via the graph-generate graph: single kind (graph), single operation (create); artifacts land in the project's `.graph-scheduler/` with one attached usage doc.

## Requirements

### Requirement: Maker journey entry point

MODIFIED: the maker journey SHALL be entered through the `graph-generate` graph — concrete, single kind (graph), single operation (create), zero repo-owner assumptions (no CONTEXT.md / docs/adr/ / openspec dependency). The graph SHALL declare a purpose-focused `description` surfaced by the pilot before execution. Skill co-production SHALL NOT be supported by the maker journey (user decision — no kind switch, no operation enum). The journey's acceptance phase SHALL deliver the ownership obligation to the user: on acceptance, the produced graph SHALL be stated as user-maintained from that point (FL3 ownership split — AI MAY have created it; once created, only the user maintains it, changes go through graph-maintain). The implement phase SHALL produce the **two-path bundle** — graph file at `.graph-scheduler/graphs/<name>.yaml` (with `$schema` + `version` self-description header, inventory, canonical key order, flow block) + registry entry at `.graph-scheduler/graphs/registry.json` — no attached doc.

#### Scenario: Maker journey resolves to graph-generate

- **WHEN** an end user in a foreign project (no CONTEXT.md, no docs/adr/) wants to produce a graph artifact
- **THEN** graph-generate SHALL run without repo-owner assumptions — scope interview proceeds directly, artifact + registry entry land under the project's `.graph-scheduler/` (two-path bundle, no attached doc)
- **AND** the pilot SHALL show the graph-generate description + resolution source before the first node

#### Scenario: Accept delivers ownership obligation

- **WHEN** the maker journey reaches its acceptance phase
- **THEN** the accept phase task text SHALL state that the produced graph is user-maintained from that point (FL3 ownership split — changes go through graph-maintain)

#### Scenario: Spec phase confirms run ending

- **WHEN** the maker journey's spec phase runs atom-graph-design
- **THEN** the spec task text instructs confirming run-ending semantics per atom-graph-spec §Run Completion (single home — consult, do not restate) and that the design proposes no end phase and no `end` routing action

#### Scenario: Producer writes the two-path bundle

- **WHEN** graph-generate's implement phase completes
- **THEN** the graph file exists at `.graph-scheduler/graphs/<name>.yaml` and the registry entry exists at `.graph-scheduler/graphs/registry.json` — no `.graph-scheduler/docs/` write occurs

### Requirement: Produced graphs SHALL carry an inventory

The maker journey's produced graph SHALL include a top-level `inventory` array (per the workflow format): one entry `{ id, type, goal, constraints? }` per phase — bounded-compound goals (connectors AND/THEN/IF-ELSE/OR — structural keywords ALL-CAPS, prose `and`/`or` lowercase; ordinary ≤ 5 steps; conditional ≤ 3 paths — the gate operand bound no longer exists), flow entries stating "expands <use> subgraph", main entries naming the executing skill in verb form and stating rework conditions in the goal when the node carries one, optional constraints drafts (one-sentence prose rules, ≤ 5 per atom, non-goals as direct negation). `type` values SHALL be `main` | `flow` only. Generated inventory goals SHALL comply with the case discipline (structural keywords uppercase). The inventory is generated by the writer at creation (AI first-generation legal per the ownership rule); afterwards it is user-maintained.

#### Scenario: Produced graph carries inventory

- **WHEN** graph-generate's implement phase completes
- **THEN** the produced graph YAML includes a top-level `inventory` array with one `{ id, type, goal, constraints? }` entry per phase

#### Scenario: Case discipline in produced inventory

- **WHEN** graph-generate produces a graph whose inventory is generated by the writer
- **THEN** the inventory goals use ALL-CAPS structural keywords (AND/OR/IF/THEN/ELSE) and lowercase prose conjunctions

#### Scenario: Maker graph self-demonstrates

- **WHEN** graph-generate's own definition is loaded
- **THEN** it carries its own inventory array in the `{ id, type, goal, constraints? }` shape

### Requirement: spec-accept SHALL offer direct end

The maker journey's `spec-accept` confirmation node SHALL offer the direct-end option on its final card. A maker who wants to end the journey mid-way (before graph production completes) SHALL be able to choose 「结束本轮（direct end）」 and end the run directly (`direct_end: true` → `graph_force_end`) — never forced to drain through unstarted production nodes.

#### Scenario: Maker ends the journey mid-way

- **WHEN** the maker confirms at `spec-accept` that they want to stop producing the graph
- **THEN** the final card SHALL present 「结束本轮（direct end）」
- **AND** choosing it SHALL terminate the run via `graph_force_end`

#### Scenario: Design accepted — production proceeds

- **WHEN** the maker accepts the design at `spec-accept`
- **THEN** graph production SHALL proceed — unchanged
